Сценарий: фоновый **`yes >/dev/null`** нагружает CPU (4 ядра, Debian trixie).

## Измерения

| Момент | uptime / free | Комментарий |
|---|---|---|
| До | load **1.81** 3.23 1.73; available **3.7 GiB** | система в покое |
| Во время | load растёт; `yes` **~100 %CPU** (PID 13082) | виновник вверху `ps --sort=-%cpu` |
| После `kill` | load **1.85** 3.19 1.73; available **3.8 GiB** | нагрузка спадает |

Команды:

```bash
yes >/dev/null &
ps -eo pid,ppid,stat,%cpu,cmd --sort=-%cpu | head -5
pstree -s -p $PID
kill $PID
```

Цепочка: `systemd → … → gnome-terminal → bash → yes`.

## /usr/bin/time

```bash
/usr/bin/time -f "%e s, %M KB" python3 -c 'sum(range(20_000_000))'
```

Результат: **0.19 s, 8464 KB** — время по часам и пиковая память процесса Python.

## Postmortem

### Симптом

04:38 — load average > 1 при **4** ядрах; интерфейс/команды откликаются медленнее.

### Причина

Пользовательский процесс **`yes`**, запущенный в фоне, занял одно ядро (~100 %CPU).

### Действия

`ps --sort=-%cpu` → PID `yes` → `pstree -s -p` → `kill PID` → повторный `uptime`/`free -h`.

### Профилактика

Не оставлять тестовые `yes`/циклы в фоне; перед нагрузочными тестами — `jobs` и `pgrep yes`; для длительных задач — `nice -n 19`.
